# 카탈로그 계약과 원본 이관

상태: 설계 및 독립 하네스 구현. 관련 작업: `DATA-001`, `HARNESS-001`.

`jpop-today/jpoptoday`의 `contracts/catalog.mjs`는 공개 후보 카탈로그의 v1 구조를 검증한다. 이 저장소에는 운영 앱과 실제 카탈로그가 아직 이관되지 않았다. `tests/fixtures/catalog.json`은 가상의 테스트 자료이며 운영에 사용하지 않는다. 계약 성공은 출처의 진위, 번호의 최신성, 사용 권리 또는 실제 데이터 이관 성공을 뜻하지 않는다.

## v1 구조

| 필드 | 계약 |
| --- | --- |
| `schemaVersion` | 숫자 `1` |
| `artists` | 비어 있지 않은 배열. 중복 없는 안정 `id`, `nameOriginal`, `nameKo`, 문자열 배열 `aliases` |
| `songs` | 비어 있지 않은 배열. 중복 없는 안정 `id`, `titleOriginal`, `titleKo`, `version`, 문자열 배열 `aliases` |
| `songs[].artistIds` | 실제 `artists`에 존재하는 ID를 하나 이상 참조하며 중복 없음 |
| `songs[].karaoke` | `tj`와 `ky` 객체를 모두 포함 |
| 제공사 `status` | `registered`, `unknown`, `unlisted` 중 하나 |
| 제공사 `number` | `registered`면 1~10자리 숫자 문자열. 전부 0인 값은 금지. 선행 0 보존. 다른 상태는 필드 생략 또는 `null` |
| 제공사 `sourceUrl` | `registered`와 `unlisted`는 비어 있지 않은 HTTPS URL. 계정명·비밀번호를 URL에 포함하지 않음 |
| 제공사 `checkedAt` | `registered`와 `unlisted`는 실제 달력 날짜인 `YYYY-MM-DD` |

`unknown`은 확인하지 않았다는 뜻이다. `unlisted`는 근거를 확인했지만 등재되지 않았다는 뜻이다. 수집 실패, 빈 응답 또는 원본 필드 누락을 `unlisted`로 바꾸지 않는다. `unknown`의 URL·확인일은 생략하거나 `null`일 수 있고, 값이 있으면 같은 형식 규칙을 적용한다.

동일 제공사 번호는 v1 공개 카탈로그에서 유일해야 한다. 번호 충돌을 자동으로 병합하거나 한 곡을 삭제하지 않는다. 곡·버전의 동일성과 원본을 검토한 뒤 해결한다. ID는 다른 제공사의 번호나 제목 변경 때문에 다시 생성하지 않는다.

검증기는 추가 필드를 제거하거나 이름·번호·출처·확인일을 보정하지 않는다. URL의 형식만 검사하므로 해당 페이지가 그 번호의 근거인지, 확인일이 실제 검토 기록인지, 저작물을 공개할 권리가 있는지는 사람이 검토하고 기록해야 한다.

## 원본과 계약 사이의 차이

조사 기준: `kim75503/todayjpop`의 커밋 `6dbe5a65d1bd729c09393f746f715f4363089a43`. 원본은 읽기 전용으로 조사했다.

`data/jpop-playlist.raw.json`의 3,299개 곡에는 기존 TJ/KY 번호가 있으나 곡 수준의 `sourceUrl`·`checkedAt`은 없다. 원본의 묶음 출처 문구나 TSV 경로는 번호를 확인한 공식 제공사 페이지와 확인일을 대신하지 않는다. 수입 날짜·현재 날짜·파일 수정일을 `checkedAt`으로 자동 채우지 않는다.

원본 KY 번호 중 다음 7개는 여러 곡에 등장한다. 이는 정체성 검토 대상이며 현재 데이터만으로 오류라고 단정하지 않는다.

| KY 번호 | 원본 등장 횟수 |
| --- | ---: |
| `43011` | 2 |
| `43060` | 3 |
| `80603` | 2 |
| `44671` | 2 |
| `40554` | 2 |
| `57803` | 2 |
| `41637` | 2 |

따라서 원본의 필드명을 바꾸는 작업만으로 v1 공개 승격이 완료되지 않는다. 자동 생성한 제공사 URL·확인일을 넣거나, 이미 관측한 번호를 `unknown`으로 바꾸고 지워서 검증을 통과시키지 않는다.

## Raw staging 전략

이관은 원본 보존과 증거 보강을 먼저 한다. 이 단계는 다음 계약으로 설계하며 아직 importer가 구현된 상태는 아니다.

1. 원본 TSV·JSON을 정확한 바이트로 보존하고 저장소, 커밋, 파일 경로, 행 번호, 파일 SHA-256을 기록한다. 운영 카탈로그와 staging은 별도 경로를 사용한다.
2. 원본 안정 ID, 기존 URL과 저장 데이터의 참조, TJ/KY 관측 번호 문자열, 제공사별 누락 상태, 제목·버전·아티스트 정보를 손실 없이 보존한다. 원본 이력은 번호의 진위에 대한 증거와 구분한다.
3. 관측 번호는 staging의 `observedNumber` 같은 별도 필드에 유지한다. 증거가 부족한 행은 `observed-unverified`처럼 staging 전용 검토 상태로 관리하고, 이것을 v1 제공사 `status`로 직접 변환하지 않는다.
4. 제공사별 공식 근거 URL과 실제 확인일을 검토 기록으로 보강한다. 접근 불가·수집 실패는 별도 수집 결과로 남기며 기존 관측을 삭제하지 않는다.
5. KY 중복 번호의 동일 곡·다른 표기·버전 여부를 검토하고 ID 매핑을 명시한다. 손실을 감수하는 묵시적 dedupe는 금지한다.
6. 증거·정체성 검토를 통과한 후보에 v1 검증과 안전 승격을 적용한다. 부분 후보가 전체 카탈로그를 덮지 않도록 대상 범위·기존 ID·행 수·번호 변화 보고를 함께 검토한다.

이관 동안 기존 서비스와 마지막 운영 스냅샷을 유지한다. 새 v1 실제 데이터 승격은 증거 보강과 충돌 검토 이후 수행하고, 합성 fixture 성공과 구분해서 기록한다. 라이선스·공개 콘텐츠 검토와 기존 URL·즐겨찾기 호환성 검증도 이관 완료 조건이다.

## 검증과 안전 승격

Node.js 22 이상, 외부 패키지 없이 실행한다. 후보와 스냅샷은 서로 다른 파일이어야 하며 출력 디렉터리는 미리 존재해야 한다.

```bash
node scripts/validate-catalog.mjs /workspace/catalog-staging/candidate.json
node scripts/promote-catalog.mjs /workspace/catalog-staging/candidate.json /workspace/catalog-staging/current.json
```

`promote-catalog.mjs`는 UTF-8·JSON·v1 계약을 검증한 다음 출력 파일과 같은 디렉터리의 임시 파일을 exclusive 생성하고, 후보의 원래 바이트를 쓰고 동기화한 뒤 `rename`으로 교체한다. 출처·확인일을 만들지 않는다. 입력 실패·빈 카탈로그·깨진 JSON·동일 경로·링크 별칭·쓰기 또는 교체 실패가 발생하면 오류를 반환하고 기존 스냅샷을 유지한다.

이 CLI는 원본 수집기에 아직 연결되어 있지 않다. 비어 있지 않은 대규모 데이터 누락, ID 변경, 범위 누락, 최신성, 외부 출처의 진위, 실제 공개 권리는 v1 구조 검사만으로 잡을 수 없다. 전체 스냅샷 수집기 통합 때 변화 보고와 출처 검토를 추가해야 한다. 자세한 검증 범위는 [하네스 문서](../engineering/harness.md)에 기록한다.
