# 여러 작업 스레드의 진행 방식

공유 상태는 채팅 기억이 아니라 GitHub Issue·PR과 이 문서 저장소를 기준으로 한다. 전체 작업은 사용자 요청에 따라 여러 스레드로 나눌 수 있다. 실제 새 채팅 생성은 사용자가 요청한 경우에만 수행하고, 내부 위임은 허용된 에이전트 기능으로 처리한다. 스레드 수를 늘리는 것 자체를 성과로 평가하지 않는다.

## 역할

| 작업 | 소유 범위 | 시작 조건 |
| --- | --- | --- |
| 통합·설계 | 스펙·ADR·호환성·릴리스 | 항상 |
| 데이터 | 수집 어댑터·계약·스냅샷·정정 | 원본 데이터 접근 |
| UI·검색 | 페이지·검색·저장 | 기준선 빌드와 ID 계약 |
| 콘텐츠 | 공개 가이드·곡 설명·출처 | 실제 검증 자료 |
| QA·배포 | E2E·접근성·성능·Cloudflare | 실행 환경·미리보기 |
| 정책·수익화 | 개인정보·광고·심사 증거 | 실제 광고 설정 접근 |

## 작업 계약

각 Issue는 목표, 스펙 ID, 저장소·파일 범위, 의존 Issue, 완료 기준, 검증 명령, 배포 영향을 포함한다. 작업자는 시작 전에 담당·상태를 기록하고 변경 브랜치를 만든다. 다른 작업자의 파일을 동시에 수정하기보다 소유 범위를 합의한다. 같은 워크스페이스를 쓰면 파일 변경이 즉시 공유됨을 고려한다.

상태는 planned → ready → in_progress → review → verified → shipped, 또는 blocked다. blocked에는 원인·증거·풀 조건을 적는다. 코드 merged와 서비스 shipped를 구분한다. GitHub labels나 프로젝트 보드가 아직 없으면 Issue 본문에서 같은 상태를 관리한다.

## 통합 순서

원본 기준선과 계약 → 데이터 어댑터·URL/저장 이관 → 상세 정적 HTML → 검색/UI → 콘텐츠 → 미리보기 품질 검사 → 운영 전환 → 심사 준비.

커밋을 공유하기 전에 원본 라이선스·출처를 유지한다. 작업 종료에는 변경 SHA·테스트·막힌 사항·다음 담당 범위를 남긴다. 스펙 변경이 필요하면 해당 문서 PR을 코드 PR과 링크하고 통합 순서를 명시한다.

사용자는 사이트 수정·검증·배포를 전적으로 위임했다. 일상 변경마다 같은 승인을 다시 요구하지 않는다. 권한·자격·개인정보 등 반드시 운영자 입력이 필요한 일만 구체적으로 요청하며 영향 없는 작업은 계속한다.
