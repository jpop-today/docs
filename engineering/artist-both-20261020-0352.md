## 구현

`confirmedNumbers`가 반환한 공식 확인 번호를 기존처럼 TJ·금영별 고유 ID Set에 넣고, 두 Set에 함께 있는 ID 수를 `both`로 계산한다. 가수 원문·안정 anchor·곡/버전 ID를 합치지 않고 전역·가수 바로가기·각 가수 그룹에 정적 HTML로 표시한다. 기존 업체별 확인 수, 합집합 ID 수와 번호 건수는 그대로 계산한다.

세 범위 모두 `data-provider-count="global|index|group"`, `data-provider="both"`, `data-count`를 제공한다. 기존 `tj`·`ky` 선택자는 유지한다. `a[data-confirmed-both-search]`는 `/search/?number=confirmed-tj&number=confirmed-ky`로 연결한다. 같은 ID의 두 공식 근거라는 뜻, 검색 두 조건의 동시 적용, JavaScript 필요와 정적 가수 목록 대안을 화면에 설명한다. 0개는 미수록 확인을 뜻하지 않는다고 명시한다.

기존 blue `#4f7cff`→pink `#ff7aa8` 상단 띠·전체 pink/mint/blue 배경을 보존했다. 새 검색 링크에는 연한 mint 배경과 최소 높이 44px를 적용했다. 600px 이하에서는 기존 업체 두 칸 아래에 두 업체 교집합 수를 한 줄로 배치하고, 바로가기의 두 업체 수는 업체별 수 다음 줄로 표시한다. 새 클라이언트 스크립트는 추가하지 않았다.

## 검증 상태

- 시작 시 읽은 소스 `git status --short`는 비어 있었고 해당 파일 diff도 없었다. 이후 공용 워크스페이스의 ledger 변경은 자료 담당 소유로 보존했다.
- 앱 파일 SHA256: `420e66830b1205136f1a6173403de025e3aa44a7098654518609ee6eb2f528d5`.
- 읽기 전용 Node projection 점검: 현재 워크스페이스 자료 3317 ID, 공식 확인 그룹 28, 합집합 36 ID, TJ 36 ID, 금영 31 ID, 교집합 31 ID, 교집합이 있는 가수 그룹 23개를 관측했다. 이는 작업 중 ledger와 기존 공식 판정을 사용한 계산 확인이며 독립 오라클·최종 승인·운영 검증을 대신하지 않는다.
- 초기 인계 시점에는 앱 빌드·Astro 타입 검사·artifact 검사·브라우저·CI·미리보기·운영 배포가 **미실행**이었다. 이후 root가 unit 377개·타입 26파일 0오류·artifact 3347파일 통과와 전용 서버 준비를 통보했고, 앱 담당은 아래 브라우저 검사만 실제 실행했다. root의 빌드와 겹치는 서버/빌드 명령을 시작하지 않았다. CI·원격 미리보기·운영 배포는 이 인계가 증명하지 않는다.
- 렌더 검증 흐름: `/artists/` → 두 업체 모두 확인된 곡 검색 → 두 `number` 조건 및 교집합 결과. 추가로 360px JavaScript off에서 정적 수·가수 anchor·기존 상세/공식 링크, 키보드/44px·콘솔·광고 요청·브랜드를 확인할 예정이다.
- `frontend-testing-debugging` 및 `browser/control-browser` SKILL을 읽고 사용 가능한 도구를 조회했다. Browser 제어 `js`·runtime·CUA 도구가 없어 연결 Browser 실행은 차단됐다. 소스 AGENTS의 기존 Playwright 경로와 작업 배정에 따라 root 제공 서버에서 시스템 Chromium으로 실제 검증했다.

## 통합 의존성

자료 담당의 실제 공식 조회·개별 검토 ledger append와 가이드 보강, 품질 담당의 독립 자료 오라클·브라우저 검사가 필요하다. root는 결과 SHA와 실제 검증 영수증을 연결해 최종 수를 기록한다. 두 동료의 읽기 전용 평가와 수정 이력은 별도로 보존한다. Google 계정·권리·법적 동의·실제 심사 상태를 앱 변경의 결과로 주장하지 않는다.
