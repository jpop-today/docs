# 다중 스레드 협업과 위임

사용자는 jpop.today의 스펙, 재설계, 수정, 검증, 배포와 여러 스레드의 협업을 위임했다. 일상 수정·PR·병합·배포에 같은 승인을 다시 요구하지 않는다. 계정 본인확인, 법적 동의, 운영 데이터나 리소스의 되돌릴 수 없는 삭제는 필요한 사용자 입력을 요청하고 독립 작업을 계속한다. 비밀 값은 환경 설정의 안전한 입력 경로로 받는다.

## 저장소별 책임

| 저장소 | 책임 | 기준 |
| --- | --- | --- |
| `.github` | 운영 규칙·기여 안내·Issue/PR 템플릿 | 현재 private. 조직 기본 파일의 자동 적용을 가정하지 않는다. |
| `docs` | 제품 스펙·ADR·하네스·진행·릴리스 기록 | 구현과 운영 판단의 근거를 기록한다. |
| `jpoptoday` | 앱·데이터 처리·테스트·CI·배포 구성 | 동작과 자동 검증의 실행 위치다. |

저장소마다 필요한 `AGENTS.md`와 템플릿을 명시적으로 둔다. 실행 워크플로는 소스 저장소에 둔다. 제품 계약을 바꾸면 docs의 스펙·ADR 변경과 소스 PR을 서로 연결한다. 조직 정책을 작성했다는 사실만으로 실제 GitHub 설정이나 브랜치 보호가 적용됐다고 표시하지 않는다.

## 작업을 시작할 때

먼저 해당 저장소의 `AGENTS.md`, 관련 스펙·ADR, [하네스](../engineering/harness.md), 진행 기록을 읽는다. 한 작업은 검토 가능한 사용자 동작 또는 운영 결과를 단위로 나눈다. 스펙 ID는 `SRC-001`, `DATA-001`, `HARNESS-001`, `SEARCH-001`, `SONG-001`, `FAVORITES-001`, `CONTENT-001`, `SEO-001`, `PRIVACY-001`, `RELEASE-001`, `ADS-001`을 사용한다.

Issue 또는 로컬 작업 기록에 다음 계약을 남긴다. 원격 Issue 생성이 막히면 `LOCAL-<번호>`를 쓰고 연결이 복구되면 실제 Issue와 연결한다.

```text
작업 ID / 목표:
스펙 ID / ADR:
담당 스레드·에이전트 / 통합 담당자:
저장소 / 브랜치 / 기준 SHA:
변경 파일·디렉터리 / 공용 파일 담당:
의존 Issue·PR:
완료 기준 / 실행할 하네스 검증:
현재 상태 / 차단 원인:
```

브랜치는 `codex/<작업ID>-<주제>`처럼 명명한다. 기준 SHA는 각 저장소의 실제 커밋으로 기록한다. 저장소가 여러 개면 SHA도 각각 기록한다. 작업 범위나 제품 계약을 바꾸기 전에 해당 기록을 갱신한다.

## 여러 스레드와 에이전트

통합 담당자는 작업 계약을 관리하고 서로 겹치지 않는 파일 범위를 배정한다. 데이터·검색·콘텐츠·검증처럼 독립 작업을 병행하되, 같은 파일·의존성 선언·lockfile·공용 타입은 한 담당자만 변경한다. 검토 담당자는 먼저 읽기 전용으로 확인하고 수정이 필요하면 파일 담당과 조율한다.

같은 체크아웃을 공유하는 에이전트 사이에서는 파일 변경이 즉시 공유된다. 시작과 인계 시 `git status`와 관련 diff를 확인하고, 다른 담당자의 변경을 덮어쓰거나 되돌리지 않는다. 브랜치 전환·commit·merge·push는 통합 담당자 한 명이 맡는다. 충돌하는 작업은 먼저 인계하거나 순서대로 실행한다. 다른 스레드가 독립 환경을 사용하더라도 원격 main과 관련 PR의 기준 SHA를 확인한다.

클라우드 작업은 이미 격리되어 있으므로 기존 체크아웃을 사용한다. Git worktree는 사용자가 명시적으로 요청한 경우에만 만든다. 새 사용자 소유 채팅은 사용자 요청이 있을 때만 만들고, 하위 에이전트에는 작업 계약과 파일 범위를 전달한다.

## 검증·통합·배포

1. 관련 스펙을 기준으로 구현하고 해당 하네스 검증을 실행한다. 명령·결과·대상 SHA와 미실행 항목을 남긴다.
2. PR에 사용자 동작, Issue·스펙·ADR, 기준·결과 SHA, 데이터·URL·저장 데이터 영향과 검증 증거를 연결한다.
3. 통합 담당자가 최신 main·범위·충돌·검증 결과를 확인한다. 실패한 필수 검증은 원인을 해결하거나 미완료로 기록한다.
4. 실제 Cloudflare 프로젝트·연결 저장소·대상 브랜치·자동 배포 여부를 확인한다. 미리보기에서 핵심 사용자 흐름과 배포 SHA를 검증하고 이전 정상 버전의 복구 경로를 확보한다.
5. 위임 범위에서 병합·운영 배포를 진행하고 릴리스에 소스 SHA, 데이터 스냅샷, 배포 ID·URL, 확인 결과, 이전 정상 배포를 기록한다.

PR 생성이 막혀 로컬 commit만 있으면 원격 PR이나 병합이 완료됐다고 쓰지 않는다. 운영 사이트를 직접 확인하지 못했으면 운영 검증을 완료로 표시하지 않는다.

| 구분 | 완료를 나타내는 증거 |
| --- | --- |
| 문서 | 스펙·ADR·운영 기록의 파일과 SHA |
| 검증 | 명령·결과·실행 환경·검증한 SHA |
| 병합 | PR URL·병합 커밋 |
| 미리보기 | URL·배포 ID·SHA·확인 결과 |
| 운영 배포 | 운영 URL·배포 ID·SHA·핵심 흐름 확인 |
| AdSense | 준비 체크 결과 / 신청 사실 / Google 심사 결과를 각각 기록 |

문서 작성·코드 병합·배포가 AdSense 승인을 뜻하지 않는다. `준비 중`, `신청 가능`, `신청됨`, `승인됨`, `수정 필요`를 구분하고 Google의 실제 결과로만 승인을 확정한다. 임의 글 수·트래픽·기간을 승인 보장 기준으로 삼지 않는다.

## 인계 양식

```text
작업 ID / 관련 Issue·PR:
결과 / 변경 파일:
기준 SHA / 결과 SHA:
실행한 검증과 결과:
미실행 검증·차단 원인:
미리보기 / 운영 배포 상태와 증거:
관련 docs·데이터 변경:
다음 담당자 / 다음 작업 / 남은 의존성:
```

실패나 접근 제한이 있어도 독립 작업은 계속한다. 같은 실패 명령을 조건 변화 없이 반복하지 않는다. 필요한 권한·도메인·변수의 이름과 막힌 작업만 기록하고 비밀 값을 문서나 출력에 남기지 않는다.

## 현재 실행 제한

2026-10-13 조사에서 기존 개인 저장소의 Git 읽기는 성공했지만 GitHub API와 운영 사이트 요청은 네트워크 `CONNECT 403`으로 막혔다. 후속 요청에서는 GitHub PR 생성·CI와 운영 HTTP 확인이 성공했다. 초기 제약과 현재 결과는 status.md에서 갱신한다. Cloudflare API는 인증 요구가 남아 배포를 실행하지 않았다. 기존 앱은 아직 조직 소스 저장소로 이관 완료되지 않았다. 이후 접근·이관·배포 상태가 바뀌면 실행 증거와 함께 운영 기록을 갱신한다.
