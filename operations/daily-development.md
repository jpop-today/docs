## 매 실행을 시작할 때

1. 세 저장소의 `AGENTS.md`, [스펙](../product/spec.md)과 관련 ADR, [실행 상태](status.md), [작업 큐](roadmap.md), [최신 확정 릴리스](releases/preview-20261013.md), 직전 일일 기록을 읽는다. GitHub의 최신 main SHA, 열린 Issue·PR, CI·릴리스·배포 결과도 읽는다. 원격 접근이 막히면 확인 시각·오류·마지막 확인 SHA를 기록하고 로컬 검토 가능한 작업부터 진행한다.
2. 클라우드 환경·네트워크의 현재 적용 상태, 필요한 도구와 비밀 binding의 준비 상태를 조회한다. 준비 관측과 해당 API 호출의 실제 성공은 구분한다. 비밀 값·전체 환경·credential 파일은 출력하거나 기록하지 않는다.
3. root가 KST 날짜와 고유 `runId`를 정하고 시작 기록에 담당자·3개 저장소의 base SHA·브랜치·파일 소유권을 남긴다. `git status`와 관련 diff를 읽어 기존 사용자·동료 변경을 보존한다. 작업자는 Git 상태 조회만 하며 브랜치 전환·commit·merge·push, package/lockfile·공용 타입·CI·배포 변경은 root만 수행한다.
4. 같은 KST 날짜·Issue에 실행 중인 작업이나 미반영 PR이 있는지 확인한다. 이미 활성 run이 있으면 새 팀을 중복 시작하지 않고 그 기록을 인계한다. root가 시작 시각·담당·runId를 Issue/일일 기록에 남겨 실행을 선점하고, 실제 동시 실행이 경합하면 한 run만 통합·보고를 게시한다. GitHub Actions의 보고 작업도 concurrency로 직렬화한다. 단순 파일 존재만으로 분산 잠금이 보장됐다고 쓰지 않는다.
5. 중단된 run은 마지막 활동·담당 상태·미반영 diff를 확인한 뒤 명시적으로 종료 또는 인계한다. 시간 경과만으로 다른 작업자의 파일을 지우거나 같은 일을 재시작하지 않는다. 이미 완료한 PR·수정·릴리스를 다시 생성하지 않는다.
6. 사용자 요청대로 해당 날짜의 새 작업자 3명을 생성한다. 전일 roster는 이력으로 보존하고 아직 실행 중인 전일 작업자는 interrupt·인계 후 현행 명단에서 제외한다. root는 각 작업자에게 목표·스펙·수용 기준·검증·파일 범위·의존성·base SHA를 전달한다.

환경을 복구할 수 없거나 외부 자료가 부족하면 `blocked`/`partial`과 증거를 남긴다. 조건이 바뀌지 않은 실패를 무한 재시도하지 않는다. 공식 근거 조사에 필요한 시간을 허용하고 독립 작업을 계속한다.

문서·조사·하네스도 할당된 수용 기준으로 평가한다. 코드 줄 수, 변경 파일 수, 외부 승인을 얻었는지로 서로 다른 업무를 비교하지 않는다. 범위 변경이나 소유권 인계는 root가 기록한 뒤 수행한다.

## 오전 보고와 완료 보고

오전 보고는 KST 09:00 예약으로 준비한다. 실제 게시 시각과 예약 시각을 함께 남긴다. 지연되거나 전일 기록이 없으면 그대로 설명한다.

- **전일 실제 결과:** 직전 완료 report·PR·CI·릴리스/배포 링크에서 확인한 개선, 실패·미실행, 차단과 남은 의존성. 전일 계획을 전일 완료로 복사하지 않는다. 기록이 없으면 `확인할 전일 보고 없음`으로 적는다.
- **오늘 계획:** 우선순위와 사용자 가치, 3명의 목표·소유 파일·수용 기준·검증, 의존 작업·계정 입력, 릴리스 후보와 통과해야 할 게이트. 실행 전 계획을 `planned`로 표시한다.

완료 보고는 통합·검증 후 해당 KST 날짜의 `jpoptoday/reports/daily/YYYY-MM-DD.json`과 `docs/operations/daily/YYYY-MM-DD.md`에 남기고 서로 연결한다. root가 이 경로에 기록을 생성할 계획이며 파일이 생기기 전에는 링크를 완료 증거로 표시하지 않는다. 재실행은 runId별 시각·결과를 보존하고 앞선 실패·투표·알림 결과를 덮어 숨기지 않는다.

보고 JSON의 실제 필드명·타입은 소스의 report schema가 기준이다. 스키마와 문서 모두 다음 의미를 보존해야 한다.

| 기록 영역 | 필수 의미 |
| --- | --- |
| 실행 | schemaVersion:1, KST date·timezone:Asia/Seoul, runId, 예정/실제 시작·완료 시각, JSON phase는 plan/complete; CLI mode morning/completed와 구분, Issue와 상태 |
| 기준과 팀 | 저장소별 branch/base/result SHA, 작업자 ID·역할·소유 파일·수용 기준, 현행/제외/신규 roster와 원인 |
| 결과 | 전일 실제 결과, 오늘 계획, 오늘 완료/부분/실패/차단, 사용자 가치, 변경 파일·PR·근거 링크 |
| 검증 | 명령·실행 환경·대상 SHA·실제 결과·로그; `passed`, `failed`, `not_run`과 이유를 구분 |
| 릴리스 | 후보/실제 버전, 의미 있는 변경, tag/릴리스 URL·SHA, CI·artifact·preview·production·복구의 개별 상태/증거 |
| 계정/자료 | AdSense 상태와 실제 통지 근거, 사용자가 해야 할 입력, 출처·권리·번호 근거의 미확인 범위 |
| 평가 | 동료별 4항목 점수·각 근거·검토한 파일/결과, 두 리뷰 합/평균, root 확인, 동률 처리·교체 상태 |
| 알림과 재개 | Discord `sent`/`failed`/`skipped`/`not_attempted`, 실제 시각/비밀 없는 이유, 다음 한 작업·의존성·다음 실행의 읽을 기록 |

알림 상태는 실제 전송 결과를 따른다. Secret 미설정은 `skipped`와 설정할 Secret 이름을 남기고, HTTP 오류는 `failed`로 남긴다. Secret 설정만으로 `sent`라고 기록하지 않으며 webhook URL·응답에 포함된 비밀 값은 공개하지 않는다. 재실행 때 같은 완료 알림을 중복 보내지 않도록 게시 단계·runId·기존 성공 기록을 확인한다.

## 동료 두 명의 실제 평가

작업자가 변경 파일·검증·미실행·차단·다음 작업을 인계한 뒤 root가 평가를 요청한다. 각 작업자는 나머지 두 작업자의 실제 파일과 검증 증거를 읽고 각각 리뷰 하나를 제출한다. 따라서 작업자마다 동료 리뷰 2개, 총 6개가 필요하다. 자기 투표는 금지하며 읽지 않은 파일의 리뷰·예상 점수·가짜 합계를 생성하지 않는다.

| 항목 | 0..5 점수의 판단 근거 |
| --- | --- |
| 정확성 | 할당된 스펙·수용 기준을 만족하고 사실/상태를 정확히 구분하는가 |
| 증거 | 실제 파일·명령·SHA·공식 자료 등으로 결과와 미확인 범위를 확인할 수 있는가 |
| 사용자 가치 | 할당 목표의 사용자 문제 또는 운영 차단을 실질적으로 개선하는가 |
| 유지보수성 | 범위·호환성·파일 소유권을 지키고 다음 실행이 안전하게 이어갈 수 있는가 |

각 항목은 정수 0..5, 한 리뷰 총점은 0..20이다. 모든 항목에 해당 파일·검증·자료와 연결한 근거를 적고, 수용 기준별 충족/미충족과 수정할 문제를 남긴다. 0은 근거로 확인한 미충족에 사용한다. 자료 부족·권한 차단·검증 불능·미시도만으로 자동 0점을 주지 않는다. 차단을 정확히 재현·보고하고 가능한 독립 결과를 냈는지도 해당 계약에 따라 평가한다.

root는 리뷰어 ID·자기 투표 여부·각 항목 범위·근거·실제 산출물·완료 기준을 확인한다. 점수와 근거가 모순되면 리뷰어에게 재검토를 요청하고 원본/수정 이력을 보존한다. 리뷰가 없으면 `pending_review`로 기록하고 실제 검토를 이어간다. 없는 투표를 대신 채워 교체를 완료하지 않는다.

작업자별 두 리뷰의 합은 0..40, 평균은 0..20이다. root가 검증한 **두 리뷰 합이 가장 낮은 작업자 1명**을 교체 대상으로 정한다. 업무 유형이 달라도 할당된 수용 기준 대비 품질을 비교한다. 동률은 두 리뷰의 정확성 합 → 증거 합 → 사용자 가치 합 → 유지보수성 합이 낮은 순으로 해소한다. 완전 동률이면 시작 기록의 `tieBreakOrder`에서 먼저 정한 작업자를 선택한다. root는 적용 규칙·근거·최종 결정을 기록하고 사후에 동률 순서를 바꾸지 않는다.

현재 문서 작성 단계에서는 동료 평가·최저점·교체 결과를 생성하지 않았다. 실제 요청과 파일 검토가 끝난 후 일일 기록에 기록한다.

## 교체와 다음 날 팀

평가 종료 시 root는 대상 작업자를 active roster에서 제외하고 실행 중이면 `interrupt_agent`로 중단한 뒤 `spawn_agent`로 새 작업자 1명을 영입한다. 새 작업자는 남은 의존성·허용 파일·기준 SHA·다음 작업을 인계받으며 현재 active roster는 3명이 된다. 교체는 실제 도구 성공과 이전/새 ID·시각·원인으로 기록한다. 생성 실패는 `replacement_pending`으로 남기고 active 3명 회복을 완료로 주장하지 않는다.

현재 도구에는 작업자의 영구 삭제 API가 없다. `active roster 제외 + interrupt + 새 작업자 생성`을 교체라고 기록한다. 원본 소스·작업 기록·리뷰·제외 명단을 삭제하지 않고 작업자 자체가 실제 삭제됐다고 표현하지 않는다.

사용자가 매일 새 3명을 요청했으므로 다음 날짜의 실행은 전일 active 3명을 그대로 재사용하지 않는다. 전일 인계를 읽고 새 3명으로 독립적으로 시작한다. 전일 종료 때의 1명 교체와 다음 날 시작 때의 새 3명 구성은 별도 사건으로 기록한다.

## 릴리스와 계정 게이트

개선한 기능·데이터 정정·검증·운영 결과가 의미 있을 때만 버전을 정한다. 내용 없는 버전 증가나 검증하지 않은 릴리스를 매일 달성한 것처럼 만들지 않는다. 게이트가 통과하지 못하면 후보·차단·다음 작업을 보고하고 마지막 정상 버전/배포를 보존한다.

릴리스 전 root는 변경 범위에 맞는 필수 검사, 동일 소스 SHA의 CI·artifact·미리보기 결과, ID/URL/storage 회귀, 출처·권리·공개 파일, 이전 정상 배포와 복구 경로를 확인한다. 일반 앱 게이트는 소스 `AGENTS.md`와 [앱 하네스](../engineering/app-harness.md)를 따른다. PR·병합·GitHub tag/release·미리보기·jpop.today 운영 배포는 각각 실제 상태·SHA·URL로 기록한다. 별도 preview 프로젝트의 Cloudflare `production` label을 jpop.today 운영 전환으로 해석하지 않는다.

AdSense 상태는 `unknown`(실제 계정 미확인), `preparing`(준비 중), `submitted`(실제 제출 근거 있음), `approved`(Google 승인 근거 있음), `rejected`(Google 거절/수정 통지 근거 있음)로 구분한다. [AdSense 운영 기준](adsense.md)과 [정책 조사](adsense-policy-review-20261013.md)를 읽고 실제 통지·확인일·다음 조치를 남긴다. 콘텐츠 수·트래픽·개발 완료로 승인을 보장하지 않는다.

계정 본인정보·소유권 확인·법적 동의·심사 제출에 운영자 입력이 필요하면 공식 입력 경로와 필요한 항목만 남긴다. 운영자 답을 만들어내거나 Secret을 채팅으로 받지 않는다. 출처·확인일·이미지/가사 권리·실제 제공사 번호를 허위로 보강하지 않으며, 관측 번호/unknown을 검증된 카탈로그로 승격하지 않는다. 차단된 계정 단계와 독립적으로 가능한 기술·근거 준비를 계속한다.

## 종료와 다음 실행의 읽을 기록

root는 일일 보고를 Issue#9와 PR/릴리스에서 찾을 수 있게 연결한다. 다음 실행은 아래 순서로 가장 최신의 실제 기록을 읽는다.

1. [Issue#9](https://github.com/jpop-today/jpoptoday/issues/9)의 최신 완료 보고/차단/활성 run과 작업 계약.
2. `jpoptoday/reports/daily/YYYY-MM-DD.json`의 최신 실제 파일과 `docs/operations/daily/YYYY-MM-DD.md`의 대응 기록: roster·실제 투표·교체·다음 작업·의존성 포함.
3. [실행 상태](status.md), [작업 큐](roadmap.md), 최신 실제 릴리스 기록과 해당 PR·CI·배포의 SHA/결과.

로컬 `/tmp`, 미커밋 diff, 켜 둔 세션·개발 서버가 다음 실행에 남는다고 가정하지 않는다. 원격 전달이 실패하면 파일 위치·실패·남은 전달 작업을 명시한다. 이 문서의 검증은 기준 문서·현재 Git 상태·문서 링크·규칙의 일관성 확인이며, 예약 실행·Discord 전송·계정 확인·릴리스/배포·평가를 실행한 증거로 사용하지 않는다.
