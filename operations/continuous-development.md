## 지속 개발의 의미와 현재 상태

클라우드에서 개발하면 사용자의 컴퓨터에 실행 환경을 유지하지 않고 작업할 수 있다. 하지만 하나의 에이전트 세션이 24시간 계속 실행되거나 무기한 유지된다는 보장은 없다. 세션 종료, 실행 시간·자원 제한, 네트워크 정책, 계정 권한 만료, 다음 실행의 환경 복구는 별도 변수다. 이번 세션의 도구 접근 성공을 다음 세션의 지속성 보장으로 사용하지 않는다.

프로젝트의 지속성은 GitHub에 보존한 소스·문서·Issue·PR·CI 결과와 명확한 재개 기록으로 만든다. 다음 실행은 마지막 작업 계약과 검증 증거를 읽고 미완료 목표를 이어 완성한다. 미리보기나 문서 한 건을 만들었다는 이유로 그날 개발이 끝났다고 판단하지 않는다. 한 결과를 검증한 뒤 실행 여력과 독립 작업이 있으면 다음 우선 작업을 계속한다. 미리보기 웹서버나 `/tmp`의 조사 복사본, 미커밋 변경, 로컬 설치 패키지가 다음 실행에 남는다고 가정하지 않는다. 클라우드 세션을 계속 켜 두는 것만으로 CI·백업·인계가 대신되지 않는다.

| --- | --- | --- |

## 매 실행의 계약

시작할 때 세 저장소의 `AGENTS.md`, [스펙](../product/spec.md), 관련 ADR, [실행 상태](status.md), [작업 큐](roadmap.md), 진행 중인 Issue·PR과 마지막 인계를 읽는다. 파일의 현재 내용과 저장소 상태를 확인한 뒤 결과 하나를 정한다. 다른 작업자의 변경을 초기화하거나 이미 진행 중인 일을 새로 시작하지 않는다.

각 실행은 한 가지 검토 가능한 결과를 남긴다. 예를 들면 호환성 결함 하나를 수정한 PR, 실제 데이터 충돌 한 묶음을 대조한 근거 문서, 미리보기의 핵심 흐름 검증 기록, 특정 권한 부족을 재현한 차단 기록이다. 많은 파일 변경 자체를 완료 기준으로 삼지 않는다.

```text
작업 ID / 관련 Issue·PR / 스펙 ID·ADR:
이번 실행 목표 / 완료 기준:
담당자 / 단일 통합 담당자:
저장소·브랜치 / 시작 SHA:
소유 파일 / 공용 파일 담당자:
의존 작업 / 필요한 권한·도구의 이름:
검증 명령 / 실제 결과 / 검증한 SHA:
현재 상태 / 실패 또는 미실행 이유:
다음 한 가지 작업 / 재개에 필요한 자료:
```

Issue를 생성하지 못하면 로컬 작업 ID를 사용한다. 접근이 복구되면 실제 Issue와 연결하되 기존 로컬 기록을 원격 생성 사실로 바꾸지 않는다. 완료한 변경은 통합 담당자가 검토·검증하여 PR·커밋과 연결하고 실행 상태를 갱신한다. 원격 전달에 실패했다면 로컬 산출물 위치와 전달 실패를 함께 인계한다.

## 여러 작업자의 실행

[협업 기준](collaboration.md)이 공통 계약이다. 통합 담당자는 작업마다 겹치지 않는 파일 범위를 배정한다. 같은 체크아웃을 공유할 때 브랜치 전환·commit·merge·push와 공용 package/lockfile·타입·배포 설정 변경은 통합 담당자 한 명이 맡는다. 검토는 읽기 전용으로 시작하고 수정이 필요하면 해당 파일 담당에게 인계한다.

의존 작업이 끝나기 전에 그 결과를 완료로 가정하지 않는다. 데이터 계약·ID·URL·즐겨찾기 키 변경은 스펙·ADR과 관련 담당자에게 먼저 연결한다. 같은 파일이 필요한 두 작업은 순서대로 진행하거나 소유권을 명시적으로 넘긴다. 서로 다른 환경에서도 PR 기준 SHA와 최신 원격 상태를 확인한다.

사용자의 요청 없이 새 사용자 소유 채팅이나 Git worktree를 만들지 않는다. 세션 안의 하위 에이전트 협업과 사이드바에 추가되는 사용자 채팅을 구분한다. 종료 시 결과뿐 아니라 미실행 검증·남은 의존성·다음 담당자를 남긴다.

## 현재 존재하는 재개 검증

조직 앱은 Node.js24 이상, lockfile 설치, Python3 읽기 helper를 사용한다. 독립 계약은 Node22 CI도 유지한다. `npm test`는 계약 검증이며 새 앱의 빌드·브라우저·실제 제공사 번호 검증을 대신하지 않는다.

```sh
cd /workspace/jpoptoday
npm test
```

Cloudflare의 현재 배포를 읽기 전용으로 확인할 때는 기존 helper를 사용한다. `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` binding이 해당 실행에 설정되어야 하며 값을 출력·문서화하지 않는다. 읽기 성공은 배포·DNS 변경·rollback 권한의 증거가 아니다.

```sh
cd /workspace/jpoptoday
npm run inspect:cloudflare -- --project todayjpop
```

Issue#5에서 앱 명령도 실제 구현·검증했다. `npm ci` 후 `npm run check`, `npm run build`, `npm run verify:dist`, `npm run test:e2e` 순서로 실행한다. 시스템 Chromium은 PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH로 지정하고, 없으면 Playwright Chromium을 설치한다. 확정 SHA의 build-info와 실제 CI·Cloudflare 결과는 [앱 하네스](../engineering/app-harness.md), [실행 상태](status.md)에서 확인한다. `npm run deploy:preview`는 clean HEAD와 동일 sourceSha artifact만 전용 프로젝트에 배포한다. 개인 원본 빌드를 조직 앱 결과로 쓰지 않는다.

## 실패와 차단 처리

실패·차단은 실행을 멈추는 이유와 계속할 수 있는 일을 분리해 기록한다. 같은 실패 명령을 원인 변화 없이 반복하거나 성공한 것으로 수정하지 않는다.

| 조건 | 상태와 남길 증거 | 이어갈 독립 작업 |
| --- | --- | --- |
| 필수 테스트 실패·공개 artifact 검사 실패 | failed, 명령·종료 상태·실패 범위·대상 SHA | 원인 수정, 관련 회귀 검증 |
| 외부 요청 차단·필요 권한 없음 | blocked, 대상 도메인·기능·HTTP 상태/오류·확인 시각 | 로컬 코드·문서·fixture 검증 |
| 세션 종료·실행 한도 도달 | partial, 마지막 완료 결과·남은 변경·재개 자료 | 다음 실행에서 계약을 읽고 재개 |
| 수집 입력 누락·잘못된 후보 | failed, 수집/검증 결과; 마지막 정상 데이터 보존 | 후보 원인 조사; 검증 없이 승격 금지 |
| 번호 출처·이미지/가사 권리 불명 | pending_review, 미확인 항목과 실제 근거 | 공개 제외 또는 미확인 표기; 허위 근거 금지 |
| 계정 본인확인·법적 동의 필요 | blocked_on_operator, 운영자가 입력할 항목과 공식 경로 | 기술 준비와 영향 없는 구현 |
| 미리보기/운영 연결 확인 불가 | blocked, 확인하지 못한 프로젝트·브랜치·SHA | 운영 전환 게이트의 독립 검사 |

실패 조건은 실행별 결과 값이다. [작업 큐](roadmap.md)의 planned / in_progress / blocked / verified / merged / shipped와 대응하여 기록하고, 테스트 통과를 병합·배포 성공으로 올리지 않는다. AdSense 준비·제출·승인은 [별도 상태](adsense.md)로 유지한다.

운영 배포 전에 같은 SHA의 CI·미리보기 결과, 기존 URL·저장 데이터 회귀, 공개 산출물, 마지막 정상 배포와 복구 경로를 확인한다. 새 앱 전환이나 배포가 차단돼도 정책 조사·콘텐츠 근거·데이터 대조를 계속한다. 운영자의 본인정보를 대신 작성하거나 비밀 값을 채팅으로 요청하지 않는다.

## 향후 예약 실행을 구성할 때

예약 실행 요청이 생기면 지원되는 Codex 자동화 도구를 먼저 확인한다. 예약 한 번의 프롬프트에는 Issue, 기준 문서, 작업 범위, 완료 결과 하나, 검증·인계·중복 실행 회피 조건을 넣는다. 매 실행이 원격 기록을 읽도록 하고 환경이 비어 있어도 재개 가능하게 만든다. 지원 여부와 실제 생성 결과를 확인하기 전에는 자동화가 작동한다고 설명하지 않는다.

GitHub Actions의 테스트·빌드·배포 workflow와 에이전트 개발 실행도 구분한다. Actions가 실행된다는 사실만으로 에이전트가 계속 개발하는 것은 아니며 예약 실행은 큐·환경·서비스 상태에 따라 지연될 수 있다. 배포·수집 작업이 중복되면 한 작업만 게시하게 하며, 예약 개발 실행이 같은 공용 파일을 동시에 변경하지 않도록 통합 순서를 관리한다.

사용자가 매회 상태 알림을 요청하지 않았다면 변화 없는 상태는 조용히 유지하고 완료·실패·의미 있는 변경·필요한 사용자 입력이 있을 때만 알린다. 실제 자동화 ID, 주기, 시간대, 실행 기록과 중단 방법을 남긴다. 자동화 설정은 현재 작업의 완료 결과로 만들어내지 않는다.

## 이번 문서의 검증 경계

이 문서는 저장소 역할·기존 명령·진행 상태를 읽고 작성한 운영 계약이다. 문서 작성 자체로 24시간 실행, 새 앱 빌드, 운영 전환, 예약 자동화, AdSense 계정 확인을 실행하지 않았다. 두 새 문서의 내부 파일 링크와 명령의 기존 정의를 확인하며, 커밋·PR·최종 SHA는 통합 담당자가 실제 결과와 함께 기록한다.
